<objective>
Decompose server/search_core.py (949 lines) and server/enforce.py (777 lines) along their existing internal seams into five right-sized modules, without changing any behavior. Maintenance phase, no REQ-IDs. This is one plan, not two. Plan validation showed search_core.py calls enforce's cluster-B functions (rrf_rank, quality_gate, source_tier) at 11 sites. Both splits therefore edit server/search_core.py and server/cli.py, and a same-wave two-plan split would conflict on those files. The work is a real linear chain executed as four serial green-to-green commits in one Dev session.

Target shape (from 03-RESEARCH.md, all line counts approximate):
- server/enforce.py (~450): query rewrite pipeline plus retry-mutation helpers.
- server/trust.py (~320, new): trust scoring, RRF ranking, quality gate, source tiering.
- server/search_core.py (~500): retry/refinement engine, quick_web_search, web_search, get_content, provider-outcome bookkeeping, shared result-shaping helpers including _try_fetch.
- server/search_deep.py (~195, new): deep_research and its multi-round fallback machinery.
- server/search_context.py (~250, new): deep_context_aware_search, its dataclasses, session-memory and pool machinery.

Tests reach into private internals by dotted module attribute, so every move requires mechanical prefix renames in test files in the same commit as the source move. Never add a re-export facade. search_deep and search_context import search_core, so a back-import is a genuine circular import.
</objective>
