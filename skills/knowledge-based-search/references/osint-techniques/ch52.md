This chapter (labeled Chapter 44 in the book) explains how an individual investigator can organize, query, and back up large collections of locally stored breach data without maintaining a full production database. The core argument is that a structured folder layout combined with a shell script is sufficient for most users, with Qgrep and SQLite available as upgrades for specific situations.

## Folder Structure and the DataTool Script

The starting point is a dedicated external SSD labeled "DATA" (on macOS at `/Volumes/DATA/`, on Linux at `/media/$USER/DATA/`). Ten subdirectories divide the collection by data type: `COMB`, `Combos`, `Databases`, `Hashes`, `International`, `Logs`, `People`, `Ransomware`, `Voter`, and `Whois`. Each folder holds a distinct category of acquired data, such as stealer logs in `Logs` or voter registration files in `Voter`.

The script is called DataTool. macOS users download it to `/Applications`. Linux users download it to `/home/` along with a `.desktop` launcher file. The script uses Zenity to present a graphical radio-button menu of 24 options. Each option prompts the user for a search term, changes directory to the relevant folder on the SSD, and runs either Ripgrep (`rg -aFiN`) or `find` with `grep`. Ripgrep handles content searches. `find | grep` handles filename searches.

The 24 menu options cover three query patterns for each major folder:

- **Filename search**: finds which files match a term so the user can copy a specific file path.
- **Content search**: runs Ripgrep across all files in a folder, with speed dependent on folder size.
- **Filename-and-content search**: accepts a file path (found in the prior filename search) and a search term, running Ripgrep only against that single file. This avoids scanning an entire large folder when the target file is already known.

Two additional options automate stealer log maintenance. "Logs Daily Sort" concatenates all `.txt` files from the Telegram Desktop download folder, removes originals, and sorts for unique entries using `LC_ALL=C sort -u -b -i -f -S 80% --parallel=8`. "Logs Weekly Merge" merges all sorted daily files with the master collection on the SSD and overwrites the master with a deduplicated result.

Informational Zenity dialogs appear before each operation. Users who find these dialogs annoying can disable them by running a `sed` command that comments out every `zenity --info` line in the script file.

To use the script with data stored on an internal drive rather than an SSD, every path beginning with `/Volumes/DATA/` in the script must be changed to the internal path (for example, `~/Documents/Breaches/`).

The macOS default Zenity package is functional but less smooth than the Linux version. An alternative Zenity build from `ncruces/tap/zenity` can be installed via Homebrew and reverted the same way if unwanted.

## Qgrep: Faster Queries with Compressed Databases

Ripgrep across 2 TB of data can take a long time. Qgrep compresses indexed data and allows queries in a fraction of that time. The workflow is:

1. Navigate to the Qgrep installation directory: `cd ~/Documents/Qgrep`.
2. Initialize a named database: `./qgrep init Voter /Volumes/DATA/Voter/` (or the Linux equivalent).
3. Build the database: `./qgrep update Voter`.
4. Query it: `./qgrep search Voter i bazzell` (the `i` flag disables case sensitivity).

In the author's test, a Ripgrep search of 36 GB of voter data took 39 seconds. The equivalent Qgrep query from internal storage took 8 seconds on first run and 2 seconds on subsequent runs within the same session (due to RAM caching). Queries against a Qgrep database stored on the external SSD took 19 seconds, still roughly half the Ripgrep time.

Qgrep databases are stored in a hidden `.qgrep` directory in the home folder, as three files per database (`.cfg`, `.qgd`, `.qgf`). Moving those files to the SSD requires specifying the full path to the `.cfg` file in every query and update command.

Three limitations constrain Qgrep's usefulness. First, the database requires approximately one-third of the original data size as additional internal storage (a 36 GB voter folder produced a 12 GB database). Second, each file being indexed must be smaller than available RAM. The update command crashes on files that exceed RAM. Third, any new files added to an indexed folder require running `./qgrep update` again before they appear in results.

The author's personal practice is to use Qgrep for a folder of phone-owner data (over 300 GB, split into files each under 32 GB) and to keep that Qgrep database on the internal drive for fast queries.

## SQLite: Deduplication and Structured Queries

SQLite is introduced for readers who want a traditional database. Installation is via Homebrew on macOS (`brew install sqlite`) or apt on Linux (`sudo apt install sqlite3 -y`).

The recommended approach for stealer logs uses a single-column table with a unique constraint, which prevents duplicate imports automatically. Setup sequence:

1. Open or create the database: `sqlite3 Logs.db "PRAGMA journal_mode = OFF;PRAGMA cache_size = -64000;PRAGMA synchronous = 0;"`
2. Create the table: `CREATE TABLE Logs(log TEXT PRIMARY KEY,UNIQUE(log)) WITHOUT ROWID;;`
3. Set display options: `.headers off` and `.mode list`.
4. Set the separator to a character never present in the data: `.separator "\a"` (the alert/bell character). This prevents SQLite from splitting lines on colons, commas, or pipes that appear in URLs and passwords.
5. Import a file: `.import /Volumes/DATA/Logs/logs.txt Logs`

Duplicate lines trigger a "UNIQUE constraint failed" error, which is intentional and beneficial. In testing, 25 GB of stealer log text produced a 30 GB database after indexing, and import took about ten minutes.

Querying with a leading wildcard (`WHERE log LIKE '%term%'`) forces a full table scan and is slow (over fifteen minutes on 25 GB). Querying with a known prefix using `GLOB` (`WHERE log GLOB 'https://inteltechniques*'`) uses the covering index and completes in one second. The `EXPLAIN QUERY PLAN` command shows whether a query will scan the full table or use the index.

Multi-column indexing for stealer logs is impractical because the data has no consistent format. URL:LOGIN:PASS, LOGIN:PASS:URL, and other separator styles all appear across different breaches.

Ongoing imports can be done in a single command that opens the database and imports without an interactive prompt.

The `VACUUM;` command compresses and optimizes the database. It requires free space at least equal to the database size. The full contents can be exported to a text file with `sqlite3 -header -csv Logs.db "select * from Logs;" > ~/Desktop/Logs.csv`.

The author recommends keeping a plain-text backup alongside the database because databases can become corrupt.

## Choosing Between Tools

The chapter ends with a direct comparison:

- If the search term could appear anywhere in a line, Qgrep is faster than Ripgrep, and Ripgrep is faster than SQLite.
- If the search term appears at the start of a line, the SQLite index is fastest, followed by Qgrep, then Ripgrep.
- If eliminating duplicate entries is the priority, SQLite is the best daily solution.
- Qgrep cannot ingest files larger than available RAM. SQLite can handle any file size.
- For most users who query data occasionally, the DataTool script with Ripgrep is the simplest and sufficient approach.

## Duplicate File Detection

The tool `fdupes` (installed via Homebrew or apt) scans directories recursively for byte-identical files with different names. Running `fdupes -r -d ~/Downloads` prompts the user to choose which copy of each duplicate to keep.

## Backups

The author stores the primary collection on a SanDisk 4 TB Extreme Portable SSD (drive label "DATA") and maintains two backup copies. The first is a second external drive labeled "BACKUP", a slower and cheaper spinning-disk 4 TB USB drive kept at the same location. The second is a replica stored off-site at a trusted home and updated monthly.

FreeFileSync handles the backup process. The recommended configuration is a Mirror sync, which makes the backup drive an exact copy of the SSD. The first run requires a full compare and can take considerable time. Subsequent runs compare only changed files and are faster. Both drives should be encrypted before use.

## Practical Context and Closing Remarks

The author describes the professional context: the firm collects over 2 TB of new stolen content weekly, parses that down to roughly 50 GB of useful data, and maintains a total collection exceeding 40 TB. A custom internal investigation portal (built by a database expert) can take a single email address and cross-reference it across breaches, ransomware dumps, stealer logs, people-search data, historic WHOIS records, vehicle data, and public APIs in 5 to 10 seconds.

Three stated use cases are: internal investigations (breach data reveals the real identity behind anonymous or alias accounts through sloppy OPSEC), client vetting (using the in-house system to verify potential clients before engaging), and client exposure monitoring (alerting clients on retainer when new breaches or logs contain their data).

The chapter closes with a reminder that breach data was stolen or exposed without consent and is routinely misused by criminals. The stated justification for sharing these techniques is their value to investigators and defenders. The author also notes that this work has been covered since the 7th edition of the book, that stealer logs and ransomware dumps represent a newer and larger-scale phenomenon, and that updated versions of the guide are available to legitimate purchasers at no extra cost through books@inteltechniques.com.
