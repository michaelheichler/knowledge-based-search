---
title: Hardware Configuration for Breach Data Collection
source: OSINT Techniques (Bazzell, Edison, 11th ed.)
---

This chapter (labeled Chapter 37 in the converted text) covers how to select and configure hardware for collecting, storing, and querying large breach datasets such as stealer logs, ransomware dumps, and public data leaks. Daily ingest can range from 50 GB to 5 TB, so hardware choices have a direct impact on whether the work is practical.

## Computer and Operating System Selection

The author no longer recommends a virtual machine for this type of work. VMs are slower for downloads, much slower for decompressing large archives, and run out of disk space quickly. External drives connected to a VM introduce a transfer-speed bottleneck.

The primary personal computer should also be kept separate from breach work. The data contains malicious files, viruses, and stealer-log payloads that can compromise a host OS. The recommended setup, in order of preference, is:

1. A dedicated macOS or Linux machine used only for breach data collection.
2. A dedicated OSINT machine with macOS or Linux as the host OS (used for both OSINT research and breach work, with caveats).
3. A Windows machine as a last resort, with awareness of the additional risks.

**macOS.** Any MacBook Pro with an M1, M2, or M3 processor is considered optimal. The internal storage on M-series machines reaches NVMe speeds (roughly 7,000 MB/s). Older Intel-based MacBook Pros top out around 2,500 MB/s. Machines with spinning disks or early SSDs are not suitable. Minimum RAM is 16 GB, with 32 GB preferred.

**Linux.** Any Linux-capable machine that can house an NVMe drive on the motherboard is suitable. The recommended OS is the latest Long-Term Support release of Pop!_OS or Ubuntu (Pop!_OS is preferred). Most needed utilities are included by default. Brand does not matter. The drive interface does.

**Windows.** Windows is not recommended as a host for this work. Data manipulation and queries are slower than on Linux or macOS, and the stolen datasets often include Windows-targeted malware. If Windows must be used, the risks are real and the configuration effort is higher.

## Drive Speed and Why It Matters

The chapter presents a speed comparison for common storage types:

| Storage type | Approximate speed |
|---|---|
| USB 3.0 flash drive | 125 MB/s |
| Traditional spinning disk (HDD) | 135 MB/s |
| Solid-state drive (SSD) | 600 MB/s |
| PCIe Gen 3.0 NVMe | 3,500 MB/s |
| PCIe Gen 4.0 NVMe | 7,000 MB/s |

A modern NVMe drive is 60 to 70 times faster than a spinning disk. With large datasets, query execution time can range from seconds to days depending on disk speed. The author benchmarked this concretely: decompressing 250 GB of stealer logs and then parsing passwords from the resulting text files took over five hours on an older Intel MacBook Pro (2,100 MB/s SSD), but only a few minutes for decompression and under ten minutes for parsing on a new M-series MacBook Pro or a Linux machine with a PCIe Gen 4.0 NVMe drive. Stealer log archives commonly expand into over two million small files, which stresses slower hardware further.

## External Drives

For readers not ready to buy a dedicated high-speed machine, an external USB-C SSD is an acceptable starting point. The author recommends a 4 TB portable SSD. Specific drives mentioned include the SanDisk Extreme Portable SSD (approximately $125 for 2 TB, $250 for 4 TB) and the SanDisk Extreme PRO Portable SSD (advertised at 2,000 MB/s vs. 1,000 MB/s for the standard model, though many computers cannot take advantage of the higher speed without USB 3.2 Gen 2x2 support). The SAMSUNG T7 Shield 4 TB SSD (approximately $240) is offered as an alternative. Mechanical drives and flash drives are not suitable for active querying. A slower spinning disk is acceptable for backup only. The author uses a Toshiba Canvio Basics 4 TB Portable External Hard Drive for backup demonstrations.

Always verify USB connector compatibility before purchasing. USB-C to USB-C is preferred. Check for firmware updates on any SSD before use (SanDisk had a known batch of failures that was later addressed via firmware).

## Encryption

All external drives should be encrypted before any data is stored on them. The chapter gives platform-specific instructions.

**macOS.** Open Disk Utility (Applications > Utilities) and use View > Show All Devices to reveal the physical device. Select the device (not the volume), click Erase, change the Scheme to "GUID Partition Map", and choose "APFS (Encrypted)" as the format. Name the SSD "DATA" and the backup drive "BACKUP" to be compatible with the author's scripts.

**Linux (Pop!_OS / Ubuntu).** Open Files, right-click the external drive, select Format, name it "DATA", choose "Internal disk for use with Linux systems only (Ext4)", enable "Password protect volume", and set a secure password. Repeat for the backup drive using the name "BACKUP". The drive will prompt for the password each time it is inserted.

**Windows.** On professional editions of Windows, right-click the drive in Explorer and select "Turn On BitLocker". If BitLocker is not available, VeraCrypt can be used for full-disk encryption, but the author reports frequent unlock failures and speed degradation with VeraCrypt on Windows, which is another reason Windows is not recommended.

## Summary Guidance

The chapter closes by acknowledging that older or existing hardware can be used to learn the techniques, but the constraints become apparent once data volumes grow. Upgrading to a machine with an embedded PCIe Gen 4.0 NVMe drive is the most impactful change for efficiency. A new MacBook Pro with 4 TB internal storage costs approximately $3,700. A 4 TB external SSD costs under $250 and is the more accessible starting point. Once software-based indexes (databases) are built from the raw data, even the external SSD approach approaches internal-drive query speeds for most lookups.
