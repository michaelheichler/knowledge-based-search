## Overview

This chapter (labeled Chapter 43 in the printed book) addresses how investigators working on behalf of victim organizations can locate, obtain, and responsibly analyze data that ransomware groups publish online. The authors' position is that ransomware data is not legitimate OSINT because it was acquired through crime. However, they argue that defensive investigators must know how to find and use it, and that leaving it solely in criminal hands causes greater harm.

## Background: How Ransomware Leaks Work

Ransomware groups encrypt a victim company's files and demand payment. When companies improved their backup practices and stopped paying, groups adopted a second pressure tactic: publishing all stolen data on public distribution sites if the ransom is not paid. The result is terabytes of documents, email messages, databases, patient records, identity documents, and financial files made freely available. Individual victim datasets in the examples reach 120 GB compressed across multiple download links on third-party hosts such as gofile.io.

## Finding Active Groups and Their URLs

The primary resource for identifying active ransomware groups and their current Tor addresses is:

```
https://github.com/fastfire/deepdarkCTI/blob/main/ransomware_gang.md
```

This GitHub page is accessible on the clear web. It lists known groups, provides links to their leak sites (most of which end in .onion and require Tor Browser), and marks sites that have gone offline. To access .onion links, install Tor Browser from https://www.torproject.org/download/ and paste the link directly into it.

The chapter uses the Everest ransomware group as a worked example. Their Tor page lists dozens of victims with download links. Each link shows a download count, which is evidence that others are actively retrieving the data and is useful when reporting breach severity to a client.

## Monitoring With Telegram and the Clear Web

Manually checking each group's Tor site is impractical. The chapter recommends the Telegram channel **RansomWatcher** as an easier alternative. The channel tracks all active groups and posts a notification when a new victim is listed. It does not host or distribute stolen files itself. An investigator can search any company name within the channel to see whether it appears in a known attack. If a match is found, the investigator can then look up the responsible group on the GitHub page and visit that group's Tor site to check whether files have been published.

A second clear-web option is https://ransomwatch.telemetry.ltd.

## Retrieving Data Through Telegram Channels

Some groups distribute data directly through Telegram rather than Tor. The chapter describes a specific October 2022 example using a channel called "baseleak," which offered 1 GB of medical data in text format. The retrieval process added deliberate friction:

1. Copy a token string from the last line of the channel post.
2. Open the Telegram bot @MotokoBot and paste the token.
3. Find the password in the post's comments.
4. Enter the password into the bot to unlock a Mega download link.

The entire process took a few minutes. The compressed file (70 MB) extracted to a CSV named data.csv of nearly 1 GB containing 92 fields per record.

## Processing Large CSV Files

The 92 fields in the example CSV included: Master Patient ID, Name, Sex, Date of Birth, DOB Approximate, Age, AgeInDays, AgeText, PrematureDays, GestationalAge, BSA, Ideal Body Weight, Height, Weight, HeightMod, WeightMod, SSN, BMI, Brand Preference, Safety Caps, Race, Language, Religion, Pregnant, Breast Feeding, Smoker, Address 1, Address 2, City, State, ZIP, Last Room, Last Hospital Number, Last Admit Date, Last Discharge Date, Last Visit Number, AllergyList, DiagnosisList, PhoneNumber, AssigningAuthority, Visit Number, Medical Record Number, Hospital Number, Room Number, CurrentOrPreviousRoom, Room, Prev Room Number, Admit Date, Discharge Date, PlannedDischargeDate, PCU, Facility Code, Service Type, Service Type Description, CommentsTextID, Physician Code, Physician, Unverified Orders, CrCl, AdminRecord, Diet Code, Diet Description, Clinical Service, PassStart, PassStop, Encounter Number, AccountNumber, AllowLateCharges, and additional internal system fields.

The authors retain only the fields needed for client notification (name, date of birth, SSN, address, and phone number) and discard explicit clinical data. Three shell commands are given for this workflow.

Extract selected columns (fields 1, 2, 3, 4, 6, 17, 27, 31, mapping to Master Patient ID, Name, Sex, DOB, Age, SSN, Address 1, ZIP):

```bash
cut -d, -f1,2,3,4,6,17,27,31 data.csv > data-cleaned.txt
```

Remove duplicate entries:

```bash
LC_ALL=C sort -u -b -i -f data-cleaned.txt > Data-Final.txt
```

Collapse repeated spaces:

```bash
sed -i 's/  / /gI' Data-Final.txt
```

Applied to the example breach, the 1 GB CSV became a 31 MB text file with 375,000 unique entries.

## OCR and Barcode Scanning of ID Images

Many ransomware datasets include scanned images such as driver's licenses (front and back), insurance cards, and passports. The authors describe an automated pipeline that handles these:

1. OCR runs on all images, documents, and PDFs to extract readable text. This step has weaknesses when source images are low quality.
2. Every image is scanned for barcodes, including QR codes and the PDF417 barcode on the back of a driver's license. The driver's license barcode encodes name, address, date of birth, and driver's license number as structured text, making it more reliable than OCR on a photograph of the front.
3. All extracted barcode text is ingested into a breach database, allowing queries by name, address, date of birth, or license number.
4. The system generates an alert if a monitored client's data appears in the ingestion results, with no manual effort required.

The barcode on the back of a passport card contains only the passport number, and the authors suggest it may be safer to present as identification when a business requests to scan an ID.

## Data Handling and Security

The chapter is explicit about how this data must be managed:

- All breach data is stored on a physically controlled, on-premise server and never in cloud storage.
- Access is tightly controlled and all activity is monitored for abuse.
- Medical condition data and clinical records are marked to be ignored when staff run queries.
- Intellectual property and internal business records are discarded after text extraction.
- The sole purpose of ingesting this data is to alert clients whose personal information appears in a breach.

The authors frame the final ethical argument plainly: this leaked data will be used by someone. Investigators can either allow it to be used exclusively by criminals, or they can use it defensively to expose those criminals and protect victims.
