## Overview

This chapter (authored by Mathieu Jacomy, Bernhard Rieder, Erik Borra, Guillaume Plique, Kenneth Christian Enevoldsen, and Nees Jan van Eck) argues that digital and computational (DC) tools for the Social Sciences and Humanities (SSH) are never finished products with a predictable life. The authors trace the lifecycle of such tools from origin through naming, feature evolution, maintenance, and eventual death, drawing extensively on the history of Gephi and Voyant Tools.

## The Landscape of DC Tools

The European Commission-funded SSHSOC project produced an open marketplace listing 2,165 tools (as of August 2024), categorized by function. The top categories are "analyzing" (548 tools), "data visualization" (344), "visual analysis" (283), "content analysis" (243), and "discovering" (194). The platform's ontology of "invocation types" identifies nine material forms: Command line, Command processor, Instruction page, Library, Local application, RESTful webservice, Script, Source code, and Web application.

The authors organize these types along two axes. The first question is whether a tool is computationally passive (instruction pages, source code as a static artifact) or active. The second, for active tools, is whether it is a component or standalone. Components include libraries (e.g., DaCy, SciKit-Learn) and RESTful web services (e.g., Textgrid). Standalone tools either lack a graphical user interface (GUI), as with scripts and command-line tools (e.g., Minet), or include one, as with local applications (e.g., VOSviewer, Gephi) and web applications (e.g., DMI-TCAT, Hyphe). Tools also divide by whether they run locally or only online.

The same device can look like a tool or an infrastructure depending on who is using it. A code library like spaCy is a dependency (infrastructure) to someone building DaCy, but a tool in its own right for someone with direct needs. Most DC tools are built by integrating existing components rather than from scratch, and each act of recontextualization, even a small one, makes a new tool for a new audience.

## Origin: Born from Practice

Because software can be duplicated and iterated at no marginal cost, the design process is continuous rather than episodic. Physical tools require minimizing prototypes. Software tools permit constant iteration. Two consequences follow. Every prototype is a tool: any working piece of software that solves a real problem can circulate and be reused without further polish, because researchers in lab-like settings will tolerate rough edges if a tool advances their work. Every tool is a prototype: no software is truly finished, because the technological environment keeps changing and requires ongoing maintenance. Gephi has been in active development for more than a decade and has not yet reached version 1.0, which its toolmakers reserve as a marker of completion.

Tools typically begin as tinkering for a specific experiment. When that tinkering meets a public, the toolmaker is forced to become an author: to manage accountability, articulate the tool's purpose, and begin treating it as a (never finished) product. Platforms like GitHub let toolmakers sustain an ongoing relationship with users, acknowledge bugs, and contextualize limitations.

## Naming and Identity

Choosing a name is a commitment with practical stakes. A name that already belongs to another tool causes confusion. A name that is a common word is hard to find by web search, as with Eytan Adar's GUESS. A name that carries unwanted connotations must be changed, as happened when Voyant Tools was originally called Voyeur. A name change has real costs: rewriting documentation, migrating websites, and making earlier citations look obsolete. Jupyter Notebooks was originally IPython Notebooks until it was spun off in 2014 by Fernando Pérez and Brian Granger.

Gephi began as "Graphiltre" (from "graph" and "filtre"), reflecting its initial focus. When it met a broader public, the team settled on a new name: G (for "graph") plus the Greek letter Phi (for "filter"), pronounced "jé" and "fee" in French, yielding "Géphi," later simplified to "Gephi" to avoid confusing an international audience. English speakers pronounce the G as in "graph," so the name is still pronounced differently in France than elsewhere.

Setting or resetting a tool's name is a claim to authorship, because the software has no clear birth moment. The history of OpenRefine illustrates the political dimension: created as Freebase Gridworks, renamed Google Refine after Google's acquisition, then renamed OpenRefine when Google transferred the project to the open-source community to remove the token of ownership embedded in the name. The tool 4CAT was built for analyzing the web board 4chan and stood for "4chan Capture and Analysis Toolkit." As it expanded to other platforms, the name became misleading. The toolmakers kept the name but reinterpreted it as "Capture and Analysis Toolkit," with a logo of four cats providing a new rationale for the numeral.

## Feature Evolution

The feature set represents both editorial and methodological choices. Additions and removals are driven by the evolving state of the art, the toolmaker's own scientific views, technical dependencies between features, funding obligations (features promised in grants), and maintenance cost.

Gephi removed support for hierarchical graphs in version 0.9.0 (2015) because maintaining that feature was too costly. The long-requested undo feature remains absent because its implementation requires tracking every user action, which is architecturally demanding. The Fieldnotes Plugin (Wieringa et al., 2019), an extension that logs user activity into field notes, showed that the necessary infrastructure overlaps with what an undo feature needs. During a 2021 coding retreat, the Gephi team worked with OpenRefine maintainer Antonin Delpeuch, learned from OpenRefine's undo implementation, and sketched a viable architecture. As of summer 2024, the feature is still in progress.

## The Burden of Maintenance

The chapter gives substantial attention to maintenance, framing it through an ethics-of-care lens drawn from Joan Tronto and Annemarie Mol. Maintenance is care directed at the tool and, through it, at methods, the research community, and the toolmakers themselves. Unlike repair, maintenance does not make an event: it prevents breakdown rather than recovering from it, and so it is invisible and hard to dramatize. The film Brazil (1985) and its character Archibald "Harry" Tuttle illustrate the contrast. Tuttle is a heroic repairman who bursts in, fixes, and leaves. Maintainers have no such dramatic moment. They live in continuous proximity to the thing they tend and are taken for granted.

Invisibility makes maintenance hard to fund. Academic institutions will fund a new feature or a specific fix, but not the ongoing preventive work of keeping a tool running. Letting a tool break before fixing it can attract attention and even funding, but at the cost of eroding user trust.

Gephi's 2013-2015 crisis illustrates the stakes. A Java update required by newer versions of macOS was incompatible with Gephi's core. The team chose to focus on rewriting the core entirely rather than patching the old one, a decision that meant two years during which most Mac users could not run the software. Rumors spread that the project had been abandoned. The release of version 0.9 in December 2015 restored confidence, but the episode forced the team to rethink the conditions of their own resilience. A 2018 blog post acknowledged: "we cannot just produce a version of Gephi that works well and let it be. It would stop working because technology changes."

Maintainability depends on code clarity, the availability of developers who know the codebase, and a flexible development infrastructure. Typical maintenance tasks include keeping dependencies up to date, deciding when not to update to an unstable release, using automated test systems, and monitoring crash reports. When Gephi's graphics library JOGL gradually stopped being maintained around 2021, the team had to rewrite the entire graphics engine, a multi-year project completed in 2024. During that period JOGL was revived by its own maintainers, so the team ultimately kept using it in the new engine. The episode changed the codebase in ways that benefit both toolmakers and users, illustrating that maintenance never simply returns a tool to its previous state.

## Tools Die

Software rots over time not because the code changes, but because the surrounding infrastructure does. Tools that rely on stable layers face slower decay. Java promises multiplatform deployment (macOS, Windows, Linux). Docker promises full control over the package environment. The web as a platform promises universal browser access. Each of these strategies adds code complexity and makes the codebase harder for others to take over.

Tools rarely survive the departure of their toolmakers. Passing a tool on requires that someone else gains sufficient knowledge of the codebase and enough motivation to take ownership. Unless the toolmaker successfully enrolls successors, the tool decays when they leave. Geoffrey Rockwell, maker of Voyant Tools, reflected that with retirement approaching, his goal is to find a way to pass the tool on in the next five years, or to let it die.

## Open Source Does Not Grant Sustainability

Open-sourcing code is often presented as a solution to the maintenance problem. The authors reject this framing on two grounds.

First, the practical argument: most open-source projects in the SSH domain are too niche to attract external contributors. Publishing source code on GitHub establishes the infrastructure for sharing, but recruiting maintainers requires active social effort at conferences and workshops, not just an open repository. Gephi has sought new developers since its founding and more actively since 2021. Barriers identified include Java being unattractive to younger developers, senior Java open-source contributors expecting financial compensation the project cannot afford, and researcher-toolmakers who have the skills to write plugins but not to work on the core. The major exception is Eduardo Ramos Ibáñez, who joined through the Google Summer of Code program in 2010, was not selected for the funded slot, continued contributing unpaid, designed major components including the "data laboratory" spreadsheet view, and became lead developer in 2018. The authors treat this as an outlier.

Second, the principled argument: the purpose of open-sourcing a DC tool should be to enable methodological scrutiny, foster reproducibility, and treat code as a commons, not to obtain free maintenance labor. Open source has real benefits (allowing scrutiny, facilitating teamwork, incentivizing good practices), but relying on it to solve the sustainability problem is naive, doomed to fail, and counterproductive. Onboarding a project is a social process, and opening the source code is necessary but not sufficient.
