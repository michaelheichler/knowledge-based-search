## Elasticsearch: Index Search

The IntelTechniques search tool includes an "Index Search" feature for databases that exceed the 10,000-record limit visible through "Index View." The investigator enters the target IP address, the index name found through "Index List," and a search term such as an email address or surname. The query runs against the remote server without downloading the full dataset.

Bazzell illustrates this with a 2019 case: he found an open Elasticsearch server holding Social Security Numbers and medical records. Rather than archive the data, he queried only his own surname, confirmed no records matched him, identified the hosting provider, and reported the exposure anonymously. The data was removed the next day.

The Elasticsearch Crawler (GitHub: AmIJesse/Elasticsearch-Crawler) may require periodic updates via `git pull`. Update commands are also stored in the "linux.txt" companion file distributed with the book.

## SQL Files via Google Dorks

SQL (Structured Query Language) files are database exports. Many breach releases, WordPress backups, and web forum exports use this format. Google dorks can surface publicly indexed SQL files containing real user data.

The search is built in stages. `ext:sql` alone returns millions of results, most of them web pages that happen to end in ".sql" rather than actual database files. Adding `"create table"` (a standard SQL statement naming schema tables) narrows to about 55,000 real SQL files. Adding `"@gmail.com"` confirms at least one live email address per file, reducing to about 10,000 results. Adding `"'password'"` (the word password in single quotes inside double quotes, which matches the literal string rather than the bare word) further reduces to about 5,400 results and indicates files with a password table. Adding a second email domain such as `"@yahoo.com"` and excluding GitHub with `-site:github.com` brings results to roughly 228 files, removing developer test databases. The same logic applies using `ext:txt` for text-format exports.

A typical SQL record contains a numeric user ID, display name, login username, email address, hashed password (often MD5), user role, internal flag codes, a registration timestamp, and a last-login timestamp. Files that load as text in the browser can be saved locally via right-click, "Save page as."

These sources carry trackers, viruses, and malicious software. A Linux virtual machine and a reputable VPN are recommended for browsing them.

## Usenet Archives

Usenet was a global network of text-based newsgroups predating the modern web. The Internet Archive preserves over thirty years of Usenet posts in two key collections: Giganews (archive.org/details/giganews) and Usenet Historical (archive.org/details/usenethistorical). Together they contain over 43 million unique email addresses linked to names and newsgroup topics.

### Building the Local Archive

Install the Internet Archive command-line tool with `pip install internetarchive`. Then generate item lists for each collection:

```
ia search 'collection:giganews' -i > giganews1.txt
ia search 'collection:usenethistorical' -i > usenethistorical1.txt
```

For Giganews, download only the CSV metadata files rather than the full mbox message files (which would take months and consume over a terabyte). Each CSV record contains date, message ID, name, email address, newsgroup, and subject:

```
ia download --itemlist giganews1.txt --glob="*.csv.gz"
```

Decompress all files recursively with `gunzip -r .`. Merge all CSVs into one file keeping only columns 1, 3, 4, and 5 (date, name, email, newsgroup):

```
find . -type f -name \*.csv -print0 | xargs -0 cut -f1,3,4,5 > Giganews2.txt
```

The Usenet Historical collection uses zip archives containing mbox files. Download with `--glob="*.zip"`, extract with `find . -name "*.zip" -exec unzip {} \;`, then pull out the "From:" lines with `rg -a -F -i -N "From: *" > UsenetHistorical2.txt`.

Merge and deduplicate both files:

```
sort -u -f Giganews2.txt UsenetHistorical2.txt > UsenetFinal.txt
```

Query with Ripgrep: `rg -a -F -i -N bazzell UsenetFinal.txt`.

Bazzell offers a pre-built merged file (12 GB, compressed to 3 GB) at a Mega.nz link in the text, containing name, email, and newsgroup fields with duplicates removed.

### Investigative Value

Searching a name can surface old email addresses that lead to unknown social profiles. Searching an email address reveals interests through the newsgroups posted to, and establishes a minimum account creation date. Searching a domain identifies all email addresses ever associated with it. Searching a username can produce confirmed email addresses from years prior.

Bazzell describes a 2019 case where a target username in the Usenet data linked to a previously unknown email address. That email matched a unique password in the Myspace breach. Searching that password in other breach data yielded additional accounts. Searching those accounts in the Usenet data revealed the target's real name. He also notes that people who were technically active in the 1990s often left newsgroup traces that mainstream media have not found.

## Ransomware Leak Sites

When ransomware victims decline to pay, criminal groups publish stolen files on Tor (.onion) websites. These publications include private documents, email archives, databases, and other files. Bazzell states this does not qualify as OSINT in his view because the data was never meant to be public. He covers it for investigators working on behalf of victim companies.

Because he cannot provide direct URLs, he offers Google queries that surface pages listing current Tor addresses for major ransomware groups: Dopple, Ragnar, REvil, Conti, Vice Society, Clop, Nefilim, Everest, and Cuba. Each query combines `".onion"`, the group name, `"ransomware"`, and `"url"`.

An alternative is Hack Notice (app.hacknotice.com). The query `site:https://app.hacknotice.com "onion"` surfaces ransomware incident notices that include Tor URLs. Clicking "View Original Source" on the resulting page attempts to open the URL in the Tor Browser. Tor Browser is required throughout.

## Stealer Logs

Stealer logs are text files produced by malware installed on victims' computers, typically through pirated software. Known variants include Azorult, Vidar, Redline, and Raccoon. The malware collects usernames, email addresses, passwords, browser autofill data, IP addresses, device names, and screen captures, then uploads everything to rented servers for sale. Because these credentials are recent, they are more likely to reflect current account access than older breach data.

Google searches for `"stealer logs" "download"` or with specific malware names can locate sources, but most results lead to criminal marketplaces requiring accounts to access downloads. Bazzell advises extreme caution.

Once a collection is assembled, Ripgrep queries work against it the same way they work against breach data. In a 2021 case, a harassing suspect used a throwaway email address with no breach history. The email appeared in stealer logs alongside a device name (Desktop-u3ty6). Searching that device name revealed all email addresses and passwords used on that machine, identifying the suspect as a 15-year-old whose computer had been infected by a pirated antivirus download.

## Storage Requirements

Collecting breach data, Usenet archives, and stealer logs at scale requires dedicated hardware. A VM with less than 100 GB allocated will exhaust space. External drives produce slow queries. Bazzell uses a dedicated Linux laptop with a 4 TB SSD internal drive that is never used for live online investigations. Linux provides protection against malicious software found in these data environments.

## IntelTechniques Breaches and Leaks Tool

The IntelTechniques search tool consolidates the main online breach search services into one interface, organized by target data type. Email address searches go to HIBP (Have I Been Pwned), Dehashed, IntelX, CyberNews, and Spycloud. Username searches go to HIBP and Dehashed. Domain searches go to Dehashed and IntelX. Telephone number searches use Dehashed. Name searches use Instagram and LinkedIn. IP address searches use Dehashed and IntelX. Password or hash searches use Dehashed and Google. Elasticsearch queries support Index List, Index View, and Index Search. A hash generator accepts a plaintext password and produces MD5, SHA1, and SHA-256 hashes for further searching.

## Section III Introduction: OSINT Methodology

The text then opens Section III, which shifts from techniques to workflow, documentation, and ethics. Bazzell frames the need with a story from the late 1990s: he investigated a sex offender making inappropriate contact with children online, observed the evidence on the suspect's computer during an interview, and testified months later from handwritten notes with no digital evidence. He describes this as unacceptable by current standards, which require forensic acquisition, detailed logs, and documented evidence chains.

Co-author Jason Edison, a 20-year veteran of a major U.S. police department and investigative lead of its Digital Crimes Unit, contributed most of the Section III content. He is also an official IntelTechniques OSINT instructor and maintains the IntelTechniques online training courses at IntelTechniques.net. Bazzell and Edison use a collective first-person "I" throughout the section but acknowledge disagreements: Edison uses Microsoft OneNote and Chrome, while Bazzell avoids Microsoft products and prefers Firefox and Linux. Both positions are presented so readers can choose what suits their workflow.
